## 开始适配
1、创建分支
```shell
git switch -c adapt/v2.3.2
```

2、正常开发：改代码、跑测试、提交（可多次提交，中间态没关系）
2.1、针对重点部分进行核对，发现问题可以进行网页抓包以辅助完成开发
```shell
git add -A && git commit -m "适配上游 v2.3.2 API 变更"
```
2.2、适配收尾两处别忘了：
- 代码：`1PanelClient/PanelShared/Models/DashboardModels.swift` 里 `PanelVersionTools.adaptedBaseline` 改成新面板版本——App 内总览页徽章、发版说明首行、release 流水线全认这一处（全仓唯一，不要在别处再抄一份版本号）
- 文档：README「面板版本适配」节的对照表补一行（客户端版本 | 适配面板基线 | 备注）

3、适配并验证完成后推送并PR
```shell
# 1. 推分支到 GitHub（分支名跟随基线，如 adapt/v2.4.1）
git push -u origin adapt/v2.4.1

# 2. 创建 PR（base 是 main，head 是你的分支）
gh pr create --title "适配上游 v2.4.1" --body "变更摘要、验证情况"

# 3. 等 CI 跑完并查看结果（两个 required check：Build & Test / L10n key 同步检查）
gh pr checks

# 4. 全绿后 squash 合并并删分支
gh pr merge --squash --delete-branch
```
3.1、网页操作 
在`git push -u origin 分支名` 之后打开仓库页面，GitHub 会出现黄条 "adapt/v2.3.2 had recent pushes — Compare & pull request"，点进去建 PR，测试跑完后点绿色的 "Squash and merge" 按钮

3.2、分支保护（2026-10-24 起）
main 已开保护：required status checks（Build & Test + L10n）+ 对管理员同样生效 + 禁 force push/删除。
- **直接 push main 会被拒**（哪怕 admin）——所有进 main 的改动一律走分支 + PR；
- 不强制走 PR（单人仓库没开 required reviews），但 push 的 PR 必须等两个 check 全绿才能 merge；
- 合并建议 Squash and merge（main 上一 PR 一 commit，对照表干净）。

## CI 类型检查超时坑（Xcode 26.6，2026-10-24 两轮实证）

CI 用 **Xcode 26.6**（本地 27.1），承担「低一档工具链仍可编译」的兼容性回归。
本地全绿 ≠ CI 绿：26.6 对某些重表达式的类型检查会直接超时报
`The compiler is unable to type-check this expression in reasonable time`，
且 gh run 的文本日志被 xcbeautify 吞掉了 file:line，只有一行 error。

**定位**（失败时 workflow 会自动上传 `test-results.xcresult` artifact）：

```shell
gh run download <run_id> -R xy2026yi/1PanelClient -n test-results.xcresult -D /tmp/ci
cd /tmp/ci && xcrun xcresulttool get --legacy --format json --path . > /tmp/xcr.json
# 解析 issues.errorSummaries[].documentLocationInCreatingWorkspace.url
# → 带 StartingLineNumber 的精确文件行号（python 正则提取）
```

**已实证的超时模式与修法**（都在重 UI 链上）：
- `.task { ... while !Task.isCancelled { Task.sleep(for: .seconds(5)) ... } }`
  内联轮询循环 → **拆成独立方法**（如 pollLoop()），循环变量加显式类型标注；
- `body` 修饰符链过长（12+ 级）→ **拆多个计算属性**分段检查
  （rootContent / statefulContent / toolbar 用 @ToolbarContentBuilder）；
- 手势长链（DragGesture + 两个 simultaneousGesture + tap + onKeyPress）→ 拆独立方法；
- `foregroundStyle(cond ? AnyShapeStyle(A) : AnyShapeStyle(B))` 之类三元包装
  → 改用直通类型（Color.secondary 本身就是 Color，不需要 AnyShapeStyle）。

**预防**：Features/AI 是编译批首位，后面的批次出错时 CI 中止、日志看不到——
新增长修饰符链的 View 主动按上面模式拆，别等 CI 试错。

## 测试断言必须 locale 无关（2026-10-24 实证）

CI 模拟器默认**英文 locale**：`L10n.t("内存分配超过宿主机总量")` 返回英文文案，
测试里 `contains("内存")` 必然落空（`contains("CPU")` 碰巧双语命中会掩盖问题，
516/517 过的假象）。测试断言文案一律与生产同源解析：

```swift
#expect(risks.contains { $0.message == L10n.t("内存分配超过宿主机总量") })   // ✓ locale 无关
#expect(risks.contains { $0.message.contains("内存") })                    // ✗ CI 必挂
```

## 文案与 xcstrings 卫生（提交前必看）

Xcode 图形界面构建会自动把 SwiftUI 字面量（`%@` 格式串、分隔符等）提取进 `Localizable.xcstrings`——构建设置已全关（SWIFT_EMIT_LOC_STRINGS / STRING_CATALOG_GENERATE_SYMBOLS 均 NO）但 IDE 这个行为拦不住，**只要用 Xcode 构建过，目录里就可能多出脏 key**（表现为 git status 里 xcstrings 莫名被改）。

```shell
# 提交前清一遍（在 1PanelClient 目录下）
cd 1panel/1PanelClient && python3 scripts/sync-strings.py --prune
```

CI 的 `--check` 是硬门禁（2026-10-21 起）：目录里存在未引用或未翻译（en 为空）的 key，L10n job 直接红——脏目录进不了 main，但别等到 CI 才发现，本地 prune 一下就好。

新增文案的正规流程（key = 简中原文，代码里用 `L10n.t("…")` / `L10n.f("…%@")`）：

```shell
cd 1panel/1PanelClient
python3 scripts/sync-strings.py                     # 1、扫源码把新 key 写入目录（此时 en 为空）
cat > /tmp/en.json <<'EOF'
{"新文案 key": "English text"}
EOF
python3 scripts/sync-strings.py --apply /tmp/en.json  # 2、灌英文翻译
python3 scripts/sync-strings.py --check               # 3、验证干净（退出码应为 0）
```

## 发版

CI 以 tag 为准：workflow 构建时用命令行覆盖把 tag 版本号和 run 号写进 IPA（`MARKETING_VERSION` / `CURRENT_PROJECT_VERSION`），**不改仓库文件**。所以第 1 步对发版本身不是必需，但建议做——让本机 Xcode 构建的版本号和线上一致，对照问题报告不混乱。

release 说明**首行会自动带上「适配面板版本：v2.4.1」**（流水线 grep 源码基线常量 `adaptedBaseline` 注入，无需手工写）：Release 页、AltStore 更新弹窗、App 内「检查更新」说明区三处都从这一行带出，用户下载前就知道适配关系。若该版本兼容多个面板版本（如补丁版），发版后用 `gh release edit` 把首行改成范围表述（见下）。

```shell
# 0、发版 commit 也必须走 PR（分支保护后直接 push main 被拒）
git switch -c release/v0.2.5
cd 1panel && NEW_VER=0.2.5
sed -i '' "s/MARKETING_VERSION = [0-9.]*;/MARKETING_VERSION = ${NEW_VER};/g" \
    1PanelClient/1PanelClient.xcodeproj/project.pbxproj
grep -c "MARKETING_VERSION = ${NEW_VER}" 1PanelClient/1PanelClient.xcodeproj/project.pbxproj   # 应输出 6

# 1、README 对照表补一行（客户端版本 | 适配面板版本 | 备注），上一行的「现行」移到新行

# 2、提交 → 推分支 → PR → CI 绿 → squash merge（同适配流程）
git add 1PanelClient/1PanelClient.xcodeproj/project.pbxproj README.md
git commit -m "chore: 版本号 0.2.4 → ${NEW_VER}（发版用）——适配面板 v2.4.1（兼容 v2.4.0）"
git push -u origin release/v0.2.5
gh pr create --title "chore: 版本号 → ${NEW_VER}（发版用）" --body "..."
gh pr checks && gh pr merge --squash --delete-branch

# 3、切回 main 同步，在 main 的 squash commit 上打 tag
git switch main && git pull --ff-only
git tag v${NEW_VER} && git push origin v${NEW_VER}    # 触发 Release IPA 工作流

# ⚠️ tag 必须打在「已在 main 上」的 commit——先推 tag 后合 PR 会导致 tag 指向
#    main 之外的 commit，虽可补救（内容一致的 PR 对齐）但纯属多余步骤（2026-10-24 踩过）
```

### 发版后核验

- Actions 里等 Release IPA 跑绿（约 10 分钟）
- release 页面应为正式版（无 Pre-release 标记），附件三件：IPA、`.ipa.sha256`、`altstore.json`
- release 说明**首行**应有「适配面板版本：v2.4.x」（流水线自动注入；缺失说明「读取适配面板基线」步骤出了问题，看该步骤日志）；altstore.json 的版本说明与 App 内检查更新说明区会自动带出同一行
- 兼容多个面板版本时，首行补范围表述（首行是 App 更新提示解析的锚点，改写时保留「适配面板版本：」前缀）：

```shell
gh release view v0.2.5 -R xy2026yi/1PanelClient --json body -q .body > /tmp/rel.md
# 编辑 /tmp/rel.md 首行 → 「适配面板版本：v2.4.0 – v2.4.1（补丁版、无 API 差异；…）」
gh release edit v0.2.5 -R xy2026yi/1PanelClient --notes-file /tmp/rel.md
```

- 用户加源地址（AltStore / SideStore 的「源」里添加，之后每次发版自动收到更新提示）：

```
https://github.com/xy2026yi/1PanelClient/releases/latest/download/altstore.json
```

### 故障处理

- **重推同一个 tag**（修完东西 `git push -f origin v0.2.x` 触发重跑）：release notes 会被追加一遍变成两份（softprops 对已存在 release 的 generate_release_notes 是追加不是替换）。处理：

```shell
# 1、修平 body（贴回单份内容；首行保留「适配面板版本：…」声明——
#    App 更新提示解析的就是这行，丢了只是少一行展示不致命，但别弄丢）
gh release edit v0.2.2 --repo xy2026yi/1PanelClient --notes "<单份 changelog>"

# 2、本地重跑 altstore 脚本刷新源里的说明（--clobber 覆盖上传）
GH_TOKEN="$(gh auth token)" TAG=v0.2.2 IPA_PATH=<IPA路径> \
  GITHUB_REPOSITORY=xy2026yi/1PanelClient bash 1PanelClient/scripts/update-altstore-source.sh
```

- **altstore.json 里版本说明为空**：曾因脚本在 CI 匿名调 GitHub API 被 runner IP 限流（已改 gh api 认证修复）；若再遇到，同样用上面第 2 条命令本地重跑即可修复。
