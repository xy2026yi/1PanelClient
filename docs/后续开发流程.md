## 开始适配
1、创建分支
```shell
git switch -c adapt/v2.3.2
```

2、正常开发：改代码、跑测试、提交（可多次提交，中间态没关系）
2.1、针对重点部分进行核对，发现问题可以进行网页抓包以辅助完成开发
```shell
git add -A && git commit -m "适配上游 v2.3.2 API 变更"
```
2.2、适配收尾两处别忘了：
- 代码：`1PanelClient/PanelShared/Models/DashboardModels.swift` 里 `PanelVersionTools.adaptedBaseline` 改成新面板版本——App 内总览页徽章、发版说明首行、release 流水线全认这一处（全仓唯一，不要在别处再抄一份版本号）
- 文档：README「面板版本适配」节的对照表补一行（客户端版本 | 适配面板基线 | 备注）

3、适配并验证完成后推送并PR
```shell
# 1. 推分支到 GitHub
git push -u origin adapt/v2.3.2

# 2. 创建 PR（base 是 main，head 是你的分支）
gh pr create --title "适配上游 v2.3.2" --body "变更摘要、验证情况"

# 3. 等 CI 跑完并查看结果（你 ci.yml 的 pull_request 触发器会自动运行）
gh pr checks

# 4. 全绿后 squash 合并并删分支
gh pr merge --squash --delete-branch
```
3.1、网页操作 
在`git push -u origin 分支名` 之后打开仓库页面，GitHub 会出现黄条 "adapt/v2.3.2 had recent pushes — Compare & pull request"，点进去建 PR，测试跑完后点绿色的 "Squash and merge" 按钮

## 文案与 xcstrings 卫生（提交前必看）

Xcode 图形界面构建会自动把 SwiftUI 字面量（`%@` 格式串、分隔符等）提取进 `Localizable.xcstrings`——构建设置已全关（SWIFT_EMIT_LOC_STRINGS / STRING_CATALOG_GENERATE_SYMBOLS 均 NO）但 IDE 这个行为拦不住，**只要用 Xcode 构建过，目录里就可能多出脏 key**（表现为 git status 里 xcstrings 莫名被改）。

```shell
# 提交前清一遍（在 1PanelClient 目录下）
cd 1panel/1PanelClient && python3 scripts/sync-strings.py --prune
```

CI 的 `--check` 是硬门禁（2026-10-21 起）：目录里存在未引用或未翻译（en 为空）的 key，L10n job 直接红——脏目录进不了 main，但别等到 CI 才发现，本地 prune 一下就好。

新增文案的正规流程（key = 简中原文，代码里用 `L10n.t("…")` / `L10n.f("…%@")`）：

```shell
cd 1panel/1PanelClient
python3 scripts/sync-strings.py                     # 1、扫源码把新 key 写入目录（此时 en 为空）
cat > /tmp/en.json <<'EOF'
{"新文案 key": "English text"}
EOF
python3 scripts/sync-strings.py --apply /tmp/en.json  # 2、灌英文翻译
python3 scripts/sync-strings.py --check               # 3、验证干净（退出码应为 0）
```

## 发版

CI 以 tag 为准：workflow 构建时用命令行覆盖把 tag 版本号和 run 号写进 IPA（`MARKETING_VERSION` / `CURRENT_PROJECT_VERSION`），**不改仓库文件**。所以第 1 步对发版本身不是必需，但建议做——让本机 Xcode 构建的版本号和线上一致，对照问题报告不混乱。

release 说明**首行会自动带上「适配面板版本：v2.3.x」**（流水线 grep 源码基线常量注入，无需手工写）：Release 页、AltStore 更新弹窗、App 内「检查更新」说明区三处都从这一行带出，用户下载前就知道适配关系。

```shell
# 1、修改版本号（本机构建同步用；CI 以 tag 为准）
cd 1panel && NEW_VER=0.2.2
sed -i '' "s/MARKETING_VERSION = [0-9.]*;/MARKETING_VERSION = ${NEW_VER};/g" \
    1PanelClient/1PanelClient.xcodeproj/project.pbxproj

# 2、验证修改版本号：应输出 6
grep -c "MARKETING_VERSION = ${NEW_VER}" 1PanelClient/1PanelClient.xcodeproj/project.pbxproj

# 3、提交并推送 main
#    注意：git commit -am 只包含「已跟踪文件」，新增文件（脚本/文档等）必须 git add 具体路径，
#    否则 CI 引用了仓库里不存在的文件会直接 127（2026-10-04 的 altstore 脚本就这么踩过）
git add 1PanelClient/1PanelClient.xcodeproj/project.pbxproj
git commit -m "chore: 版本号 0.2.1 → ${NEW_VER}"
git push origin main
#    发版前建议瞄一眼 git status，确认没有意外漏掉的 ?? 未跟踪文件

# 4、打 tag 推送，触发 Release IPA 工作流（正式版 + 自动生成 AltStore 源）
git tag v${NEW_VER} && git push origin v${NEW_VER}
```

### 发版后核验

- Actions 里等 Release IPA 跑绿（约 10 分钟）
- release 页面应为正式版（无 Pre-release 标记），附件三件：IPA、`.ipa.sha256`、`altstore.json`
- release 说明**首行**应有「适配面板版本：v2.3.x」（流水线自动注入；缺失说明「读取适配面板基线」步骤出了问题，看该步骤日志）；altstore.json 的版本说明与 App 内检查更新说明区会自动带出同一行
- 用户加源地址（AltStore / SideStore 的「源」里添加，之后每次发版自动收到更新提示）：

```
https://github.com/xy2026yi/1PanelClient/releases/latest/download/altstore.json
```

### 故障处理

- **重推同一个 tag**（修完东西 `git push -f origin v0.2.x` 触发重跑）：release notes 会被追加一遍变成两份（softprops 对已存在 release 的 generate_release_notes 是追加不是替换）。处理：

```shell
# 1、修平 body（贴回单份内容；首行保留「适配面板版本：…」声明——
#    App 更新提示解析的就是这行，丢了只是少一行展示不致命，但别弄丢）
gh release edit v0.2.2 --repo xy2026yi/1PanelClient --notes "<单份 changelog>"

# 2、本地重跑 altstore 脚本刷新源里的说明（--clobber 覆盖上传）
GH_TOKEN="$(gh auth token)" TAG=v0.2.2 IPA_PATH=<IPA路径> \
  GITHUB_REPOSITORY=xy2026yi/1PanelClient bash 1PanelClient/scripts/update-altstore-source.sh
```

- **altstore.json 里版本说明为空**：曾因脚本在 CI 匿名调 GitHub API 被 runner IP 限流（已改 gh api 认证修复）；若再遇到，同样用上面第 2 条命令本地重跑即可修复。
