## 0. 核心矛盾（为什么需要这份方案）

| 事实 | 数据 |
|---|---|
| 上游节奏 | **月度功能版本**（v2.2.3→07-07 / v2.2.4→07-27 / v2.2.5→08-06 / v2.3.0→09-14），紧急修复随时发小版本 |
| 客户端适配面 | **513 个端点**（枚举 512 case + 裸路径 ~11 + WebSocket 3）、**42 个模型文件 8,874 行** |
| 兼容机制 | **零版本分支、零能力探测**——版本号只用于「显示 + 更新对比」，README 的「请用 v2.2.5」纯靠文档约定 |
| 上游 API 稳定性 | 无公开 API 契约承诺；v2.3.0 已出现「**防火墙管理功能整体重构**」级别的模块级重写 |
| 高风险模型 | Database 88 个非可选字段、AIAgent 88、Container 69、Firewall 58——上游一处字段口径变化即整页 decode 失败或空列表 |

**结论**：适配面每月都在变大，而防线目前只有「大面积可选化」这一道隐性护栏。跟上月度节奏不能靠「出问题再修」，需要下述四层防线 + 一套标准化对齐流程。

## 1. 四层适配防线（策略分层）

### L0 版本感知层（立即做，成本最低收益最大）

现状：`SettingInfo.systemVersion` 已从 `/core/settings/search` 拿到面板版本（`DashboardModels.swift:146`），但只用于关于页显示和更新对比。

- **登录后版本比对提示**：`systemVersion` ≠ 适配基线版本时，在关于页/服务器详情温和提示「面板版本 v2.3.0，客户端适配 v2.2.5，部分功能可能有差异」。不做强阻断（面板小版本补丁不破坏兼容，误伤率高）。
- **语义化版本比较**：现 `hasUpdate(comparedTo:)`（`DashboardModels.swift:176-194`）是字符串不等即「有更新」，rc/beta 会误报——改为分段数值比较。
- **版本-适配矩阵落档**：README 的适配声明同步维护「已验证版本区间」（如 v2.2.3–v2.2.5），用户报障时先对表。
- DEBUG 解码失败日志已有（`APIClient.swift:172-190` 打原始响应）——保持，这是 schema 漂移的第一现场。

### L1 解码防御层（模型加固，按风险清单推进）

上游字段变化的破坏路径 = 「非可选字段 decode 失败 → 整页崩/空」。把仓内已有的**防御性孤例推广为默认模式**：

| 已有范式（孤例） | 位置 | 推广方向 |
|---|---|---|
| 形状透传 `CronjobPassthroughStrings/Ints`（null/标量/数组三形状兼容，按原形状回传） | `Cronjob.swift:465-525` | 导出/回写型请求（计划任务已做；容器更新回写是下一个候选） |
| 逐字段 `try?`（单字段类型变化不整页失败） | `OpenRestyManage.swift:72` | 详情页大模型（ContainerInfo 系列读改写回传字段） |
| 宽松数值 `LenientNumber` | `AIDownloaderModels.swift:14-17` | 监控/统计类数值字段 |
| 空列表回退 `EmptyInitializable`（code=200 且 data=null → 空集合） | `APIClient.swift:538-552` | 已全局生效，保持 |
| 键大小写不敏感 `from(dict:)` | `SnapshotModels.swift:160-184` | 未抓包确认过的接口 |

**加固优先序**（按「非可选字段数 × 页面重要性」）：
1. 列表信封 `total: Int` 非可选（`Website.swift:25`、`Container.swift:21`）→ 改可选 + 默认 0。上游 total 置 null 时现在会**整页失败**，这是最脆的一环。
2. `Models/Database.swift`（88 非可选）、`Models/AIAgentModels.swift`（88）——批量可选化，配解码测试。
3. `ContainerInfo` 读改写回传链（`Container.swift:312-441`）——上游加字段后回写会**丢字段**，改「原始 JSON 保留 + 覆盖修改字段」的 merge 模式。
4. `PanelRelease.version`（`DashboardModels.swift:200`）等零星非可选。

### L2 功能降级层（模块级容错）

面板有社区版/专业版、已安装/未安装、版本新旧多种形态，客户端已有三个可推广的降级范式：

- **404 降级**（`NodeManageView.swift:397-402`：nodes/list 404 → 回退静态本机节点）→ 推广为 APIClient 层的通用策略：**模块首页请求 404 时，该模块入口显示「面板版本不支持此功能」而非报错**。这对 v2.3.0 防火墙重构尤其重要（见 §3）。
- **许可证门禁**（`AdvancedFeatureGate.swift`：xpack 功能按 license 显隐）→ 已覆盖 WAF/GPU 监控/vLLM 等 6 项，新 xpack 功能持续挂进来。
- **双前缀并行容错**（`PanelBasicSettingsView.swift:529-540` core/settings 与 settings 并行 try?）→ 仅用于已知的 transitional 差异，不新增（会掩盖真实错误）。

## 2. 月度迭代 SOP（跟随上游发版的标准流程）

上游每月一个功能版本。建议固定节奏（T = 上游 release 日）：

```
T 日      上游 release → 读 changelog → 按模块分诊（见下方分诊表）
T+1~2 日  源码 diff（三源法，见 §2.2）→ 产出「字段/端点变更清单」
T+3~5 日  测试环境抓包验证 → 更新模型 + 测试夹具 → 实现/适配新功能
T+6~7 日  回归（242 用例 + 模块冒烟）→ 发版（客户端小版本）→ README 适配声明更新
```

### 2.1 changelog 分诊表（哪些变更必须跟）

| 变更类型 | 必要性 | 客户端动作 |
|---|---|---|
| **模块级重构**（如 v2.3.0 防火墙） | 🔴 必须 | 专项：端点重扫 + 模型重对齐 + 页面重抓包（见 §3） |
| 现有接口字段/口径变化 | 🔴 必须 | 模型 diff → 加固 → 解码测试 |
| 新功能（AI/模型/监控等） | 🟡 按 roadmap | 评估用户价值后排期，新端点进枚举 |
| 专业版/xpack 新增 | 🟢 挂门禁 | AdvancedFeatureGate 挂载即可，不阻塞 |
| UI/交互优化（web 端） | ⚪ 记录 | 仅当影响交互对齐假设时跟进 |
| 纯 bug 修复 | ⚪ 记录 | 若修复了客户端 workaround 对应的 bug，回收 workaround |

### 2.2 三源 diff 法（1Panel 是开源项目，这是最大杠杆）

抓包不是唯一手段——**上游 Go 后端源码就是 API 契约**：

1. **Swagger 源**：`archive/doc/1panel_api_doc.json` 已有 v2.2.5 基线。新版本导出新 Swagger（或从源码 `docs/` 目录取），脚本对比 paths + schema，自动产出「新增/删除/变更端点表」。上游若无现成 Swagger，用 `swag` 从注解生成。
2. **路由源码源**：diff 上游仓库两个 tag 的 `backend/…/router/` 目录（v2 前缀 `/api/v2` 的路由注册即端点全集），捕捉 Swagger 缺注解的端点。
3. **DTO 源码源**：diff `backend/…/dto/` 目录的结构体 json tag——这是字段级变更的权威来源，比抓包更完整（抓包只能看到当时返回了什么，源码能看到可能返回什么）。

三源交集 + 客户端 513 端点清单做矩阵，即得精确影响面。

### 2.3 抓包验证（现有工作流的标准化）

现有 archive/logs 已有按模块的抓包 md 与 samples/。标准化为：
- 每个模块一份「接口-响应样本」配对（部分已有：MySQL 状态 2026-09-14、容器 2026-09-14、iptables 2026-09-16）
- 样本 JSON 直接进 `1PanelClientTests` 做解码夹具（现状 79 处「抓包」注释在测试里，已经这么做了——补齐未覆盖模块即可）

## 4. 工程化建设（防适配面继续失控）

### 4.1 端点登记合一（立即，0.5 天）

现状端点散在三处：`APIEndpoints.swift`（512 case）+ Features 裸路径 ~11 处（`AppStoreTab.swift:590`、`AIAgentCreateView.swift:466`、`CronjobsViewModel.swift:349/361/377`、`DatabasesView.swift:62/337`）+ WebSocket 3 处。裸路径全部收编进枚举，**保证做上游 diff 时单点可扫**。

### 4.2 契约测试体系（随每次对齐滚动增强）

- 现有 242 用例中已有大量真实抓包 JSON 夹具——把「模型 × 样本」覆盖矩阵列出来，缺口模块补样本
- 每次上游对齐：新样本进夹具 + 旧样本保留（防退步）——**这使「字段加固」有回归保障**
- 可选进阶：解析失败样本注入测试（模拟上游字段类型变化，断言 L1 防御层生效而非崩溃）

### 4.3 新页面/新功能 checklist（把审查报告变成流程）

本次审查的债务几乎全部落在 v0.1.15→v0.1.20 新增代码上。在新模块 PR 自查表加入：
- [ ] 表单页 `formWidthLimit` / 日志页 `contentWidthLimit(860)`
- [ ] 三态齐全：LoadingStateView / ContentUnavailableView / LoadErrorStateView（不自绘）
- [ ] 删除操作对照风险分级表选确认方式；批量 ≥ 单删强度
- [ ] 文案全走 `L10n.t/f`（含 enum rawValue 动态查表）；日期格式化带 `L10n.locale`
- [ ] 新端点进 `APIEndpoints` 枚举；响应模型字段可选化；抓包样本进测试
- [ ] 状态色用语义令牌；等宽字体用 dataMonospaced 家族；sheet 走 `bottomSheetDetents`

### 4.4 令牌能力补齐（与本次审查 P2 联动）

`dataMonospaced` 令牌补 `dataMonospacedBody` 等档位后，用脚本批量替换 178 处硬编码——一次性终局 B2 遗留，此后 checklist 保证不再新增。

### 版本支持策略（建议，需决策）

**跟随最新版 + N-1 宽容**：客户端始终对齐最新面板版本；对 N-1 保持「尽力兼容」（L1 防线保证不崩，新功能不可用有明确提示）；不做 N-2 及更早的支持承诺。理由：单人项目适配面 513 端点，多版本矩阵不可持续；L0 提示让旧版本用户自知。

## 6. 风险与决策点

| 风险 | 应对 |
|---|---|
| 上游无 API 稳定承诺，重构随时发生 | L2 降级层是兜底；月度 SOP 缩短暴露窗口；防火墙专项验证降级模式有效性 |
| AI 模块上游迭代极快（71 端点、v2.2.x→v2.3.0 连续加账号类型） | AI 模型已全可选化（做得最好）；新账号类型按「枚举 + 通用表单」设计，避免每类型一页硬编码 |
| 抓包环境依赖（需要真实面板 + 数据） | 三源 diff 先行，抓包只做验证；测试夹具沉淀降低对环境的重复依赖 |
| 专业版功能无法自测 | AdvancedFeatureGate 门禁 + license 服务器验证（已有先例）；xpack 端点只做形状防御 |
| 单人带宽 | 里程碑按 0.5d 粒度切分可中断；M1 防火墙专项优先级高于一切 P2 债 |
